5  Storage, backup, recovery, and access

As part of a Data Management Plan, careful consideration should be given to the physical storage and security of research data. Appropriate storage procedures are essential to minimise the risk of accidental data loss, for example through overwriting raw data, loss of a device, hardware failure, or server malfunction.

In the most serious cases, loss of study-generated data may be irreversible. For example, measurements collected during a clinical visit may be impossible to reproduce once the participant has left the study.

It is therefore particularly important to ensure that study-generated data are stored securely and that appropriate backup and recovery procedures are in place. These procedures should ensure that data can be restored in the event of hardware failure, server failure, accidental deletion, or other forms of data loss.

5.1 Storage of data and metadata

There are four main data environments that will be used in DP-Next: REDCap, Fitrockr, GenomeDK, and Statistics Denmark. REDCap and Fitrockr are primarily used for data collection, while GenomeDK will serve as the primary storage environment for study-generated data, which is the place we are most responsible for setting up not only the storage, but also the subsequent safety and security of the data. Register-based analyses and linkage between DP-Next data and Danish national registers will take place within Statistics Denmark’s secure research environment. Register-based microdata will therefore not be transferred to or stored on GenomeDK.

5.1.1 GenomeDK (GDK)

GDK provides several storage areas. We will use the project storage in their Open zone for the DP-Next project (see a description of the zones here). These locations are designed for collaborative data and are eligible for backup. We do not need a Data Processing Agreement with GenomeDK as our host organisations Aarhus University (AU) and Aarhus University Hospital (AUH) already have an agreement in place which will cover us.

5.1.2 REDCap

REDCap is a secure web application for research databases and e‑forms. It stores data in a PostreSQL database and related files in a controlled file area (“File Repository”). AU provides REDCap facilities for both the University and AUH employees. The File Repository is intended for storing data and study files, but it should not be the primary long‑term file storage for bulk data; we will export and archive data into our primary storage (GDK) using the API facility provided by REDCap. As with GDK we don’t need a Data Processing Agreement for the same reasons as above.

5.1.3 Statistics Denmark

Register-based data used in DP-Next will be accessed and analysed within Statistics Denmark’s secure research environment. Study-generated data required for linkage with national registers will be transferred securely to Statistics Denmark in accordance with their procedures for external data. Only data required for the approved research project will be transferred.

The register-based data and any DP-Next data transferred to Statistics Denmark will be subject to Statistics Denmark’s rules for data security, confidentiality, data minimisation, and disclosure control.

5.2 Backup and recovery

When looking at backup and recovery we again have two situations. With the Fitrockr system we will need to trust that what is stated in the contract is also what Fitrockr is doing, and that backup and recovery is possible without any significant loss of data. We also need to trust REDCap’s system, as the setup is done entirely without any user engagement.

Where we will play a role is with GenomeDK, as described below it is the responsibility of the user to set up the files for backup, although it is not possible for us to check that a recovery is possible, as backup is still done by the GDK team.

5.2.1 GenomeDK

GDK runs its own disk‑based backup at a remote site. By default nothing is backed up. There is guidance given on the GDK website which details how the backup should be set up. It is the responsibility of the individual study teams to set this up correctly, but help can be requested from the GDK team (in particular to check that the folders have been set up correctly).

Backups are conducted once per week and retained for 14 days and it is possible to review recent backup runs. Though, it is recommended that larger files are kept out of the backup structure and only added in compressed format. At present we don’t believe that we will have any files that require this, but it will be something that we will keep under observation (see section on data volume).

We will back up the original raw data, the cleaned data in Parquet format, and the metadata. As we do not expect to do any analysis in the main study folder (see section on Sharing Data) we don’t expect to be backing up any analysis scripts or results here. This will be done in separate project folders which will be set up to only back up scripts and results.

5.2.2 REDCap

There isn’t any information on the website for REDCap at AU about backup and recovery, but we have received the following reply from the team maintaining the servers in answer to our questions about the procedures in place.

“AU-IT performs daily backups of the REDCap application and the data contained within it. All backups are managed under IBM’s Tivoli Storage Manager and stored in encrypted form. Ubuntu servers are configured to automatically install security updates. A monthly vulnerability scan is carried out using Tenable Security Centre. In accordance with Aarhus University’s annual information security cycle, a system and data classification is conducted at least once a year, followed by a risk assessment. In addition to the regular annual classification, a new risk assessment is carried out whenever significant changes are made to the system.”

5.2.3 Fitrockr

Backups, retention, recovery, and export options are governed by our contract with them. The Fitrockr contract draft should specify backup frequency, encryption, location (EU/EEA), recovery time, and access/audit reporting. We will confirm these parameters during contract finalization and update this section once the contract is signed.

5.2.4 Statistics Denmark

Storage, backup, and recovery of data held within Statistics Denmark’s research environment are managed centrally by Statistics Denmark. The DP-Next research team will therefore not maintain separate backups of register-based microdata or linked datasets outside this environment.

Register-based microdata cannot be copied from Statistics Denmark to local computers, GenomeDK, or other storage environments. Consequently, recovery and continuity of the underlying register-based datasets rely on the infrastructure and procedures maintained by Statistics Denmark rather than project-specific backup procedures.

Analysis code and other non-sensitive material may be maintained separately where permitted, but any files containing microdata will remain within Statistics Denmark.

5.3 Access to the main data structures

Only a limited number of authorised individuals will have access to the full research dataset, and access will be granted on a need-to-use basis. Users will have personal accounts with strong password requirements, and two-factor authentication (2FA) will be required where supported by the relevant system.

Currently, the project manager and relevant members of the Seedcase Project team, including the data architect, will have access to data on GDK where this is required for transformation of raw data into Parquet files and creation of metadata. No scientific data analysis may take place without prior approval of the relevant project synopsis by the steering Committee.

Fitrockr staff may have technical access to back-end data where required for operation of the platform. This access is governed by the applicable contract.

5.3.1 GDK

Access is managed on a project folder basis. GDK maintains logs and states it records login and file access events to help ensure GDPR compliance. We have been informed that we will be receiving regular reports from the system once we start using the site. These will be reviewed and signed off by the project team when we receive them.

5.3.2 REDCap

REDCap provides a logging module that automatically records project‑level activity (e.g., data exports, data changes, user creation/deletion). We will review logs on a monthly basis and after any major change. This will be done by the project team on the back of an automated email sent out by REDCap encouraging project owners to check through their log files and access controls once a month.

5.3.3 Fitrockr

We will rely on the Fitrockr contract agreement for access control, audit reporting cadence, and data‑sharing/export mechanisms. We expect that Fitrockr will be able to provide us with either access to a list of users with data viewing access, or such a list upon request.

5.3.3.1 Statistics Denmark

Access to register-based and linked data at Statistics Denmark will be restricted to users who are affiliated with an authorised institution, have been granted access to the specific DP-Next project, and fulfill Statistics Denmark’s requirements for working with microdata. User credentials are personal and may not be shared.

Only researchers who require access for an approved DP-Next analysis will be granted access to the relevant project data. As with other DP-Next data, access for scientific analyses will require an approved project synopsis in accordance with the DP-Next publication procedures.

Microdata and other information at the individual level may not be transferred out of Statistics Denmark’s research environment. Only analysis results that have been sufficiently aggregated and comply with Statistics Denmark’s statistical disclosure control requirements may be transferred. Researchers are responsible for ensuring that material transferred from the research environment does not contain microdata or otherwise allow identification of individual participants.
